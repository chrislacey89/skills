# Changelog

## v1.20.0 — The dependency graph moves onto the `gh` CLI, and `/qa` finally joins it (#205)

#168 made the slice dependency graph queryable, but built it out of hand-rolled REST calls — a numeric database-id lookup per edge, a `POST` per edge, and three documented "sharp edges" for agents to trip over. `gh` v2.94.0 had shipped `gh issue edit --add-blocked-by` on **2026-06-10**, taking issue numbers and several blockers per call. #168 landed 2026-08-04, nearly two months later. The platform did not move underneath us; the CLI support was already there and was never checked for. Two of the three sharp edges turned out to be artifacts of bypassing the CLI rather than properties of GitHub, and one of them — *"`gh issue list --json` cannot see dependency data"* — was simply false, propagated verbatim into four skills after `--json isBlocked` (a field that does not exist) was mistaken for the whole family being unavailable. Implements #205's Mediator "proceed broadly" verdict; net line count across the five skills is negative.

### Changes

- **`/prd-to-issues` §7 wires edges with the CLI (#205)** — the `BLOCKER_ID=$(gh api … --jq .id)` lookup and the `POST` collapse into `gh issue edit <blocked> --add-blocked-by <n>,<n>`. The database-id warning goes with them: it existed only because the raw endpoint takes an id where the flag takes a number. A new pitfall replaces it, and this one is real — **never pass `--blocked-by`, `--parent`, or `--type` to `gh issue create`**, which applies relationships as a deferred second mutation and, on failure, suppresses the issue URL while offering a `--recover` prompt that invites a duplicate issue. Verified live in gh 2.97.0; the fix ([cli/cli#13899](https://github.com/cli/cli/pull/13899)) is open and unmerged. Creating bare and wiring in a second pass is what makes that failure isolated and retryable, so §7's create-then-reference structure is now load-bearing rather than incidental.
- **`total_blocked_by` retires two fallback paragraphs (#205)** — `/execute`'s Blocked-slice gate and `/help`'s frontier query each read only `blocked_by`, which counts *open* blockers and so reports `0` both for "blockers all closed" and for "no edge was ever written." Both skills carried prose conceding the ambiguity was unresolvable. It is resolvable: `total_blocked_by` counts blockers regardless of state, so `total > 0 && blocked_by == 0` is the first case and `total == 0` is the second. Both paragraphs now describe a check. `/setup-ralph-loop` gets the same correction in both copies of its FRONTIER selection — AFK is the stage least able to absorb a wrong pick.
- **`/qa` gets labels and edges (#205)** — the one issue-filing skill #168 never reached. New Step 4b reads `gh label list` plus recent issues' labels and matches the existing convention, asking before creating anything new; there is deliberately no fixed taxonomy, because `/qa` runs in repos it does not own. Breakdown filing now wires one edge per prose `Blocked by` entry and reconciles the two representations. The gap was not cosmetic: `/execute`'s gate reads edges `/qa` never wrote, so a bug filed as genuinely blocked read as takeable — two shipped skills disagreeing about what "blocked" means.
- **Labels are load-bearing because sub-issue search is broken (#205)** — verified while scoping this: GitHub's `parent-issue:` qualifier does not work. The sub-issue progress badge links to a query the search backend rejects, and `has:parent-issue` matched **all 131 issues** on a repo with **zero** sub-issues. Reproduced on a second unrelated repo, so it is search-backend behavior. A shared label is currently the only mechanism keeping a batch of related issues retrievable by someone who was not in the filing session — which is why the labeling half of this change is not decoration.
- **`README.md` states the repo's first version floor (#205)** — `gh` ≥ 2.94.0, plus the GHES matrix (3.17+ for types and sub-issues, 3.19+ for dependencies). The flags are used unconditionally; the alternative of keeping a REST fallback for older `gh` was rejected because it would preserve the exact mechanism this change deletes.
- **Deliberately unchanged** — the prose `## Blocked by` block everywhere it appears (it carries the *reason* a slice is gated, which the sidebar cannot hold); native **sub-issues**, deferred on the filterability finding above rather than on cost, since `--add-sub-issue` is now nearly free; §7's hand-comparison reconciliation, which Martraire would want automated and which remains #168's debt; `/triage-issue`, which inherits the same labeling gap but files single issues rather than graphs.
- **Every dependency read moves to the CLI too, once the node shape was verified (#205)** — implementation initially kept the `gh api` reads, because the inner node shape of `--json blockedBy` had no live edge to check against and an unverified `jq` path does not belong in a skill. Wiring one throwaway edge and removing it settled it: nodes carry `{id, number, state, title, url}`, `state` is the GraphQL enum (**uppercase** `OPEN`/`CLOSED`, where REST returns lowercase — a `jq` filter copied between the two silently matches nothing), and `totalCount` counts blockers in every state, making it the CLI's equivalent of `total_blocked_by`. That removed the last reason to keep raw REST on this path, including §9's second confirming call: reading edges directly is not subject to the post-write staleness window that call existed to close. The two REST traps are retained as documentation for anyone who does drop down — PRs in the issues list, and the summary objects being absent from the single-issue `GET`.

## v1.19.1 — The review-currency stamp becomes a contract the repo can check, not prose two skills happen to agree on (#184)

v1.19.0 shipped a marker string that spans two skills — `/pre-merge` Phase 4 writes `<!-- reviewed-at: <sha> -->` into the PR body, `/closeout` Step 2 reads it back and compares it to `headRefOid` — with no shared definition of the string's shape. The writer emitted a full 40-character SHA and said so; the reader accepted 7 to 40. `headRefOid` is always 40 characters, so a short SHA reaching that marker would parse successfully and then compare unequal *forever*: `/closeout` reporting divergence on a PR whose head had not moved. No incident yet; this was found by reading the two halves against each other while scoping #182. The failure would have been silent and self-reinforcing — a second false-positive source in a gate that #163 had already been bitten by one false positive on, training exactly the reflexive click-through #163's own Skeptic Case warned about.

### Changes

- **`/closeout` Step 2 requires exactly 40 hex characters (#184)** — the extraction regex tightens from `\{7,40\}` to `\{40\}`, so reader and writer now agree on one width. The prose branched on "the SHAs match" / "the SHAs differ" without ever saying which comparison it meant, so the check is now stated outright: exact string equality on two full OIDs, never a prefix test. A malformed marker no longer takes the interrupting "divergence" branch — it fails to parse, yields an empty `$REVIEWED_SHA`, and takes the honest "no stamp found" branch, which already degrades gracefully by design.
- **`/pre-merge` Phase 4 states the invariant beside the template (#184)** — `<full-sha>` and `<short-sha>` sit on adjacent lines in the block being substituted into, with nothing marking them as non-interchangeable. The bullet now says the HTML comment carries the full 40-character SHA and the short form belongs only in the visible prose line, and gives the reason: `headRefOid` is 40 characters, so a short SHA can never compare equal.
- **`scripts/test-review-currency-marker.sh` makes it mechanical (#184)** — the new suite **extracts** the real sed script from `closeout/SKILL.md` and the real marker template from `pre-merge/SKILL.md` rather than restating either, then round-trips one through the other. That is the design crux: a hand-copied regex in a test can drift alongside the thing it tests, whereas a suite that reads both halves fails precisely when they stop agreeing. Twelve assertions cover the round trip, rejection of 7/8/12/39-character and 41-character and non-hex markers, an unmarked body, and a duplicated stamp resolving to the newer SHA rather than the stale one. Wired into the CI `script-tests` job and lefthook pre-push.
- **Prevention the repo had already written down (#184)** — `docs/solutions/architecture-decisions/staleness-gate-intermediate-writers-2026-08-06.md`, shipped *with* #163, named this class under Prevention → Code-level: "when a gate's contract spans two skills via a marker string, add a consistency check to the repo's existing test harness so the writer's emitted format and the reader's parser cannot drift apart silently. Absent that, a broken contract is indistinguishable from a legitimately un-stamped artifact — both take the no stamp found branch." The repo diagnosed the failure mode and shipped the contract without the check; this closes that gap.
- **Deliberately unchanged** — the gate's non-blocking character and three-outcome shape; the `/compound` false positive (#163's unremediated Concern, still tracked in the solutions entry); `SYSTEM-OVERVIEW.md`, which describes the loop's behavior rather than the marker's string format, and would be the wrong home for a width invariant. Not #182 either — that proposal consumes this marker but does not own its format.
- **Unblocks #182** — scoping a bounded review-response loop to the post-review delta requires the marker to be reliable across repeated passes.

## v1.19.0 — Review currency at the merge gate: `/closeout` checks that the approval still covers the diff (#163)

The pipeline reviewed a branch once and merged it later with nothing tying the two events together. `/pre-merge` read the diff and printed findings; `/closeout` merged the PR; in the intended linear flow those are the same diff, which is exactly why the gap was invisible. Real HITL sessions accrete scope on a branch *after* its review pass. On the triggering incident (a downstream client repo), `/pre-merge` passed a 29-line CI lockfile guard, then follow-on turns in the same session grew the branch roughly tenfold — a frontend test harness, a hand-rolled typed WebSocket fake, protocol tests, and a new dependency — none of it re-reviewed. A later manual read found two real defects in the un-re-reviewed code. The single review pass had silently certified an early subset of what was about to merge. Framed as "the operator forgot to re-run a skill" the fix is exhortation, which fails silently (Norman's blame reversal); framed structurally it is an inflow with no feedback loop — the same argument that produced `/closeout` itself, one seam over. Implements #163's Mediator "proceed narrowly" verdict.

### Changes

- **`/pre-merge` stamps the SHA it reviewed (#163)** — the PR body gains a `## Review Currency` block carrying an HTML-comment marker (`<!-- reviewed-at: <sha> -->`) for machines and a visible line for humans skimming the PR. Durable GitHub state, not a local file: a hook fires only in-session and would not survive the fresh `/closeout` session that typically does the merge (Norman — knowledge in the world, because prospective memory fails silently). Written at the **end of Phase 4** rather than at PR creation, which is a deliberate departure from the issue's suggested placement — the stamp asserts "a review completed at this SHA," so writing it in Phase 2 before the dimensions run would certify a review that had not happened. Phase 2 keeps a forward pointer so the PR-body mechanics stay discoverable. Reviewer-mode does not stamp: it never rewrites someone else's PR body, and its findings are unposted drafts with nothing reviewed in to certify.
- **`/closeout` Step 2 gains a review-currency precondition (#163)** — the three existing checkboxes asked whether a review happened, never whether it covered the diff about to merge. The new check reads the stamp, compares it to `headRefOid`, and branches three ways. Matching SHAs pass **silently** — announcing a non-event every run is what turns a gate into wallpaper. An absent stamp (hand-authored PR, external contribution, or a PR predating the stamp) is noted in one line and continues, because absence of a stamp is not evidence of an unreviewed diff and stopping on every un-stamped PR is the alarm fatigue that gets a gate reflexively defeated. A divergence prints `git diff --stat` and `git log --oneline` for the post-review delta, then asks once (re-review / acknowledge / stop) with re-review recommended.
- **Proportionality is the design crux, not a nicety (#163)** — the issue's Advocate and Skeptic both cite Meadows, and reconciling *add-the-missing-loop* against *policy resistance* is what the shape above is for. Showing the delta's **magnitude** rather than merely announcing that a delta exists is what makes the response proportional to a one-line typo fix versus a tenfold scope addition. A force-push that rewrote the reviewed commit out of existence is called out explicitly as a *stronger* divergence signal than a measurable delta, not a weaker one — the reviewed diff is simply unrecoverable.
- **Never hard-blocks (#163)** — `/closeout` stays HITL and non-blocking by design. The fix is making the divergence *visible*, not seizing the merge decision from the user. `/pre-merge` likewise stays advisory; it still does not set a formal GitHub `reviewDecision`.
- **`SYSTEM-OVERVIEW.md` records the loop (#163)** — Step 7.5's prose enumerates closeout's preconditions, so a fourth one that went unrecorded would leave the canonical overview describing a gate the skill no longer runs. Step 7's Output line names the stamp, and the Handoff Table's `/pre-merge` row reflects it. Bundled copies re-synced in the same commit: `SYSTEM-OVERVIEW.md` ships into four skills, and a partial edit is the #143 drift mode.
- **Deliberately unchanged** — not a hook and not an `init-pipeline` change (a local hook does not survive a fresh `/closeout` session); `/pre-merge`'s advisory nature; `/closeout`'s non-blocking character; and the two downstream defects that surfaced the incident, which map to existing `/pre-merge` dimensions and were skipped rather than missing.
- **Revisit if** — the check never fires across a sample of runs (the linear flow really does not accrete post-review → demote to an advisory line), or users always choose "merge anyway" on non-trivial deltas (behavior unchanged → move the trigger to the execute→pre-merge handoff, #115).
- **Unblocks #182** — that proposal's bounded review-response loop treats this stamp as a hard prerequisite, since scoping a re-review to the delta requires knowing which SHA the last review covered.

## v1.18.0 — A queryable frontier: native GitHub issue dependencies alongside the prose "Blocked by:" line (#168)

Turns the slice dependency graph from something the pipeline *documents* into something it can *query*. `/prd-to-issues` recorded dependency order as prose in issue bodies, so every downstream consumer reconstructed the graph by parsing English — `/help`'s signals #3/#4, `/prd-to-issues`'s own handoff line, and three copies of the Ralph loop prompt that said "respecting blocking relationships," an instruction with no mechanism behind it. The prose also never recomputed: it still read `Blocked by #47` after #47 merged. GitHub's native issue dependencies serve the same graph as a single call, and `blocked_by` counts open blockers only — so closing a blocker un-gates its dependents with zero bookkeeping. Implements #168's Mediator "proceed narrowly" verdict: strictly additive, the prose stays, each representation gets a distinct job.

### Changes

- **`/prd-to-issues` §7 wires the edges (#168)** — the existing create-then-reference second pass now also POSTs one edge per `Blocked by` entry, with the `--jq .id` database-id lookup shown inline (the endpoint takes the numeric id, **not** the `#number` and not the `node_id` — passing the wrong one wires a wrong edge or silently none). Three verified sharp edges are stated where the query is written: `gh issue list --json` cannot return dependency data at all (`--json isBlocked` errors with `Unknown JSON field`), the REST issues list returns pull requests alongside issues so `select(has("pull_request") | not)` is required, and verification reads the `/dependencies/blocked_by` list endpoint rather than `issue_dependencies_summary`, which can be served stale right after a mutation.
- **Precedence, plus a reconciliation mechanism (#168)** — the prose `## Blocked by` block documents *why* a slice is gated and survives a tracker migration; the native edge is the authoritative gate for automated selection. Naming a winner settles disagreements but does not prevent them, so §7 also reconciles the two sets at the one moment both are written together (Martraire, *Living Documentation* Ch. 3: redundant knowledge needs a divergence check, not a declaration of authority; Hunt & Thomas on DRY). This closes the "two sources of truth" objection from #168's own Skeptic Case, and came out of the library consultation the issue deferred to implementation time.
- **Every selection site uses one rule (#168)** — `/help` gains the frontier call in its Phase 1b parallel batch (returning `number`, `blocked_by`, and `assignee` in one request) and points signals #3/#4 at `blocked_by == 0`; `/prd-to-issues` §9 computes the handoff slice with a query scoped to the decomposition's own slice numbers; `/execute` Step 0 gains a blocked-slice gate that names open blockers and stops rather than discovering the gap mid-implementation. All three agree by construction rather than coincidence.
- **The Ralph loop prompt gets a mechanism (#168)** — all three copies (`setup-ralph-loop/SKILL.md` ×2 and `SYSTEM-OVERVIEW.md`) compute the frontier in bash and hand the model a candidate set, keeping deterministic selection in the script and the judgment call it is good at (which candidate is riskiest) in the prompt. `ralph.sh` recomputes each iteration, so a slice un-gates the moment its blocker closes. Edited together with `sync-skill-references.sh` run in the same commit — `SYSTEM-OVERVIEW.md` is bundled into four skills, so a partial edit would leave the pipeline stating two different selection rules (the #143 drift mode).
- **Worked examples updated (#168)** — `docs/example-pipeline-artifacts.md`'s four slices show the prose line plus its native edge, with the QA slice's fan-in flagged as the set most likely to be under-wired by hand.
- **Deliberately unchanged** — the prose `Blocked by:` line (explicitly not removed), sub-issues as the PRD↔slice link, backfilling edges onto existing open slice issues, and `/qa`'s issue template, which produces the same prose-only pattern and is left for a follow-up.

## v1.17.0 — `/visual-recap` anti-mimicry gate: recaps stay visually independent of the app under review (#146)

Closes an adherence gap in the canonical skeleton #126 introduced. That skeleton exists to stop run-to-run drift on the theory that "copy the token core verbatim" would hold — but nothing caught its violation. ### Changes

- **Step-5 adherence gate mirrored into both surfaces (#146)** — `/visual-recap` Step 5 gains a token-core adherence check beside the existing #129 Mermaid render-confirm gate; `/walk-commits` mirrors the same one-line gate in its callout-rendering discipline, keeping the two review surfaces aligned. Bundled reference copies re-synced.
- **Deliberately unchanged** — the canonical token values, block markup, Grounding Rule, secret-redaction, and the Mermaid render-confirm gate. ## v1.14.0 — Render branch-point handoffs as next-step menus (#115)

Closes a friction loop at the seams between skills. Every primary skill already computes its successor — the `Comes next by default:` line — but leaves it in prose, so the user rereads it (or remembers it) and retypes the command. The most common case is typing `/pre-merge` the instant `/execute` finishes. The fix moves that already-known next step out of the user's head and onto the screen: at genuine branch points, the handoff is offered as an `AskUserQuestion` menu with the recommended step pre-surfaced.

### Changes

- **New `docs/next-step-menu.md` convention (#115)** — one shared reference defining *when* a handoff becomes a menu (genuine branch points and high-frequency control-yield seams) and *when not* (linear single-successor handoffs, where an auto-invoke already fires, in place of a deliberate checkpoint, or on AFK runs). Option-shaping rules: recommended step first, ≤4 options, no hand-rolled "Other" (the platform supplies a free-text escape hatch), and context-specific follow-ups allowed — mirroring `/walk-commits` step 3, the existing in-repo precedent.
- **Four-skill pilot (#115)** — `/execute` offers a menu at its *manual* exits (user declined the PR-review item, or is batching) with **→ `/pre-merge`** recommended plus 1–3 run-specific follow-ups; `/pre-merge`, `/shape`, and `/closeout` render their real forks as menus. Bundled `docs/next-step-menu.md` into each via `scripts/skill-references.manifest` + sync.
- **`CLAUDE.md` §Handoff Contract note (#115)** — records the convention where skill authors look for handoff rules, stating the menu *renders* the `What comes next` line and *composes with* existing auto-invokes rather than replacing them.

### Motivation

The incident is everyday friction: the user "almost always" types `/pre-merge` immediately after `/execute`, a step the pipeline already predicted. Framed as a design failure rather than a user one (Norman's blame-reversal), the handoff keeps *knowledge in the head* when the answer is already written down and belongs *in the world*; the text-box handoff is, in Nudge's terms, an unintentionally-designed choice environment whose default action requires typing — sludge. The `/improve-pipeline` dialectic cited Norman to opposite ends — *knowledge in the world* (do it) vs. *featuritis* (don't put a menu on every seam) — and resolved the tension on scope, landing at "Proceed narrowly": menus only at genuine branch points and the high-frequency `/execute` → `/pre-merge` seam, with the recommended next step as the default option (Nudge's master lever). Deliberately unchanged: `/execute`'s auto-invoke of `/pre-merge` on the confirmed "Ready for PR Review" path (the menu serves only the manual exits), the deliberate Step 5 verification checkpoint (the menu appears after it, never instead of it), AFK/Ralph runs (no user to ask), and the linear single-successor handoffs (`/research`, `/write-a-prd`, `/prd-to-issues`). Filed alongside #66 (consolidate the conversational-principles block) so the two shared references cross-reference the platform-tool note rather than duplicate it. If the pilot proves low-cost and well-liked, the named follow-up is to extend menus pipeline-wide.

## v1.13.0 — Add `/closeout` for the merge + worktree-teardown tail (#109)

Fills the pipeline's named-but-unowned tail. Both the diagram and `SYSTEM-OVERVIEW.md` Step 9 drew the path as `… → /pre-merge → merge → /compound → cleanup`, but no skill owned `merge` or `cleanup` — the merge, worktree teardown, branch prune, and base pull were all left to the user's memory. ## v1.6.2 — Boundary-map drift checks + non-dry path sanity

Four changes tighten the contract between planning, execution, testing, and review. The through-line is the same failure mode seen from different angles: upstream slice artifacts that drift from reality, dry-run paths that hide production defaults, and tests whose timing behavior quietly degrades after retry or backoff logic is introduced. This patch adds checks at planning time, execution time, review time, and TDD time, then trims the new wording so the guidance stays scoped to issue-based slice work instead of reading like a universal preflight.

### Changes

- **`/execute` new Consumes verification gate** — Step 0 now adds a scoped check for issue-based slice work created by `/prd-to-issues`: when a slice's `## Boundary Map` / `### Consumes` section references an already-closed upstream slice, verify the declared symbols still exist at the declared path and shape before implementation starts. - **`/prd-to-issues` new Consumes plausibility check** — boundary-map drafting now verifies `Consumes` entries that reference already-closed upstream slices before finalizing the new slice, and requires a post-hoc correction comment on the upstream issue when drift is found.

### Motivation

The pack already treated boundary maps as contracts and verification as a first-class stage, but the failure mode where a closed upstream slice claimed outputs it did not actually ship was still under-specified. The same was true for dry-run CLI paths that can mask placeholder defaults and for tests that quietly become wall-clock-coupled after retries or sleeps are introduced. This patch closes those gaps without changing the pipeline shape: the new guidance is strongest where the repo is already opinionated — explicit handoffs, GitHub-native truth, and verification over assumption — and the follow-up cleanup keeps the language narrow enough that normal one-off execution work does not inherit unnecessary ceremony.

## v1.6.1 — /help base-branch detection + parallel tool-use gotcha note

One fix to `/help`'s Phase 1 state gather. The prior version hardcoded `git log main..HEAD || git log master..HEAD` to count commits ahead of base, which exit-128'd in any repo whose default branch is not `main`/`master` (this pack's own repo uses `prod`; others use `develop`, `trunk`, or team-specific names). Because `/help` dispatches its snapshot commands as a parallel tool-use batch in Claude Code, and because Claude Code cancels the in-flight siblings of any bash call that errors, a single bad ref killed the entire snapshot and forced a full retry.

### Changes

- **`/help` Step 1 split into Phase 1a and Phase 1b** — Phase 1a detects the base branch sequentially using `git symbolic-ref refs/remotes/origin/HEAD` with fallback through `main`, `master`, `prod`, `trunk`. Phase 1b dispatches the six read-only snapshot commands in parallel, each referencing the detected `$BASE_BRANCH`. If `origin/HEAD` is unset and no fallback candidate exists, the skill asks the user for the base branch name before continuing.
- **New "parallel tool-use gotcha" note in `/help`** — explicitly documents that one failing bash call in a Claude Code parallel batch cancels its siblings, and that this is why base-branch detection must run first and alone. Discourages the shortcut of chaining `&&`/`||` against a guessed branch inside a parallel batch.

### Motivation

Caught while running `/help` in the Civic Mirror repo (default branch `prod`). The initial state gather exited 128 on `git log main..HEAD`, which canceled the other six commands in the same parallel batch, and the recovery round had to retry everything with the correct ref. Two compounding problems: (1) the hardcoded branch name was wrong for the repo, and (2) the parallel dispatch amplified one failure into seven. Fix (1) addresses the immediate bug; fix (2) is a durable note so future skill authors know not to trust `&&`-chains inside parallel batches.

## v1.6.0 — BMAD Audit Adopts + /execute Auto-Flow + QA/Triage Restructure

Seven changes: five derived from the audit in `docs/bmad-comparison.md` against [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD), a flow improvement that folds `/pre-merge` invocation into `/execute`'s existing manual verification checklist, and a restructuring of the bug path so `/qa` is the single entry point for bug conversations and delegates per-issue to `/triage-issue` when depth is needed. None of the seven changes the pipeline's core shape. Together they harden review, lower the friction of trivial changes, add the orientation and recovery affordances the pack was missing, remove the manual handoff step when the user is already at the PR-ready moment, and collapse two overlapping bug entry points into one.

### Changes

- **New skill: `/help`** — side-route orientation skill that reads current repo state (branch, open PRs, open issues, `research.md` presence, milestones) and recommends one next pipeline step with a one-line reason and the specific state signals that triggered it. Advisory only — never runs the recommended skill itself. Twelve-rule priority table covers the common pipeline states from "open PR on current branch" down to "clean slate, start with `/shape`."
- **New skill: `/correct-course`** — side-route recovery skill that turns the `SYSTEM-OVERVIEW.md` Pipeline Recovery prose into an invocable workflow. Captures the trigger, diagnoses which upstream skill's output is now untrustworthy, lists every stale artifact (`research.md`, PRD issue, slice issues, open PR, planning milestone), walks the cleanup one decision at a time, and hands off to the earliest affected skill with scoped re-run instructions.
- **`/pre-merge` minimum-findings guard** — Phase 4 now counts findings across all three tiers before presenting. If fewer than 4 surfaced on a non-trivial diff (>50 changed lines or >2 files), the skill does one more focused pass for common miss categories (scope drift, silent assumption changes, shallow modules, happy-path-only tests, new state files). Borrowed from BMAD's `bmad-review-adversarial-general` "at least ten issues" rule and tuned to our context — explicit anti-sycophancy guard that stops the review from closing too early.
- **`/execute` trivial-task exception** — Step 0 TDD classification gate now allows skipping classification via direct `.claude/.tdd-skipped` creation for single-commit cleanups (typo fixes, dead code removal, comment-only changes, formatting-only changes, dependency bumps without API changes). Guarded by four conjunctive conditions: not tied to a GitHub issue, not on an active feature branch, single commit, no behavior change. When any condition fails, use the normal gate.
- **`SYSTEM-OVERVIEW.md` handoff table** — new one-row-per-skill table added before the existing Default Handoff Map bullets. Covers all 23 skills with `Expects | Produces | Next` in ≤15 words per cell. Scannable orientation for readers who do not want to read the narrative bullets. Borrowed from BMAD's `module-help.csv` declarative flow model, adapted to markdown.
- **`/execute` → `/pre-merge` auto-flow** — Step 5's manual verification checklist now has a final "Ready for PR Review" item. When the user confirms it, Step 6 cleanup runs and `/execute` automatically invokes `/pre-merge`, passing the PRD issue number forward so slice lineage and boundary map contracts can be verified without re-asking. When the user answers "no" to the PR review item — batching with more work, waiting on external input, sitting on the branch — Step 6 runs cleanup and `/execute` exits cleanly for manual `/pre-merge` invocation later. AFK Ralph iterations and trivial-task flows that never reached Step 5 keep the prior clean-exit behavior. This is not from the BMAD audit — it came from observing that HITL users already run `/execute` → `/pre-merge` sequentially every time, so folding the transition into Step 5's existing user gate removes a redundant manual step without loosening the consent checkpoint.
- **`/qa` ↔ `/triage-issue` restructure** — `/qa` is now the single entry point for bug conversations and gains a new **Step 3.5 "Decide depth"** gate applied per issue. Lightweight issues (clear repro, obvious cause, uncontroversial fix) continue through the normal filing flow. Issues that fail the depth check — user explicitly asks for diagnosis, regression from working behavior, no confident hypothesis after Step 2 exploration, intermittent repro, or multiple symptoms possibly sharing an upstream cause — delegate to `/triage-issue` for that one bug. The triage issue replaces the lightweight issue `/qa` would otherwise have filed, and control returns to the `/qa` loop for the next observation. `/triage-issue` is recategorized from side-route to invoked helper and should no longer be called as a direct entry point. A single QA session can produce a mix of lightweight `/qa` issues and deep `/triage-issue` issues without the user having to pre-classify the whole batch.

### Documentation updates

- `README.md` — skill count 21 → 23, new "Orientation & Recovery" section with `/help` and `/correct-course`; `/triage-issue` description in the Development table rewritten to reflect per-issue invocation from `/qa`; `/qa` description in the Workflow table rewritten as the single entry point for bug conversations
- `SYSTEM-OVERVIEW.md` — side-route list, handoff map bullets, directory tree, and quick reference table all include the two new skills; new handoff table section above the existing bullets; `/execute` row in the handoff table and the `/execute → /pre-merge` handoff map bullet both note the auto-invocation; `/qa` and `/triage-issue` rows rewritten to describe the per-issue delegation and return-to-loop behavior; `/triage-issue` moved from side-route to invoked-helper list and from the SIDE ROUTES tree section up into the invoked-helper group; quick reference table collapses the prior two bug-path rows into "Run a QA session or report bugs" and "Investigate a specific bug deeply"
- `CLAUDE.md` — side-route list updated; `/correct-course` noted as the invocable front door for Pipeline Recovery; `/help` described as advisory orientation; new `/execute` key-interactions bullet describes the `/pre-merge` auto-invocation and which flows skip it; `/triage-issue` moved from side-route to invoked-helper category in Invocation Roles
- `docs/using-this-pack.md` — side-route list updated with descriptions; new "Start with `/help`" and "Start with `/correct-course`" entry points added; prior "Start with `/qa` or `/triage-issue`" entry rewritten as a single `/qa` entry with an explicit note that bug sessions should not start with `/triage-issue` directly
- `correct-course/SKILL.md` — "What This Skill is NOT" and "Do not use it for" sections updated so the bug-path redirect points at `/qa` only, noting that `/qa`'s per-issue depth check delegates to `/triage-issue` when root cause is needed

### Motivation

The audit against BMAD-METHOD (`docs/bmad-comparison.md`) surfaced twelve dimensions of comparison and cut the adopt list to the five highest-value items:

1. `/help` — BMAD's strongest idea this pack lacked. A router that reads state and tells you the next step makes every other pipeline investment more discoverable.
2. `/correct-course` — the Pipeline Recovery section of `SYSTEM-OVERVIEW.md` already documented backtracking, but it was prose. Turning it into a named skill gives it a front door.
3. Minimum-findings guard — `/pre-merge` was sometimes closing with two or three findings on large diffs because the agent found nothing obvious and stopped. A re-pass threshold hardens this cheaply.
4. Trivial-task exception — the TDD classification gate is load-bearing but creates friction on single-line cleanups. An explicit, guarded opt-out reduces the "pipeline is all-or-nothing" feeling without loosening the gate for real work.
5. Handoff table — BMAD's declarative `module-help.csv` is more scannable than narrative handoff prose for orientation. A markdown table gives most of that benefit without adding a CSV.

The audit also named five things deliberately not adopted (agent personas, filesystem-first state, story-level cadence, separate market/domain/technical research skills, post-hoc test generation) and five distinctive values to defend (mandatory research with Phase 0 version check, GitHub-native state discipline, compounding `docs/solutions/`, TDD classification gate, boundary maps before implementation). Those trade-offs are now durable in `docs/bmad-comparison.md`.

The sixth change — the `/execute` → `/pre-merge` auto-flow — is not from the audit. It came from observing the actual HITL workflow: the user was already running `/execute` followed by `/pre-merge` every time, so the explicit handoff was friction. Three options were considered: (A) auto-invoke with no prompt, (B) a separate Step 7 with its own confirmation, (C) fold the transition into Step 5's existing manual verification checklist as a final item. Option C won because it reuses the existing user-consent checkpoint instead of adding a new one, preserves the "the user decides when the PR happens" property, and naturally skips AFK Ralph and trivial-task flows where Step 5 does not run.

The seventh change — the `/qa` ↔ `/triage-issue` restructure — came from the same observation pattern. The prior model treated `/qa` and `/triage-issue` as two separate direct entry points for bug work, forcing the user to pre-decide whether a bug session was "lightweight intake" or "deep diagnosis" before starting. In practice most QA sessions mix both: three cosmetic bugs that just need filing, one regression that needs root cause, one intermittent failure that needs reproduction. Making the user re-enter a different skill mid-conversation was friction, and more importantly it meant `/triage-issue`'s depth was often skipped for bugs that silently needed it. Per-issue delegation from inside `/qa` lets a single conversation handle the mixed case without renegotiating scope. `/triage-issue` is still a distinct skill with its own rigor — it just stops being the thing the user reaches for directly.
